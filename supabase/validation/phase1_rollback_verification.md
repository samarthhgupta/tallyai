## Rollback Order

The script reverses migrations in reverse sequence (I → A) within a single transaction:

```
Migration I  →  DROP TABLE voucher_classes
Migration H  →  DROP COLUMN party_type, pref_source from vendor_ledger_preferences
Migration G  →  DROP TABLE customer_masters
Migration F  →  DROP COLUMN sales_ledger_config from companies
Migration E  →  DROP COLUMN tax_direction from duties_taxes_masters
Migration D  →  DROP COLUMN voucher_class, party_name, party_gstin from rejection_archive
Migration C  →  DROP COLUMN voucher_class, source, source_profile_id from invoice_batches
Migration B  →  DROP all Phase 1 columns from invoices (7 columns)
Migration A  →  DROP TABLE pos_import_profiles (last, because invoices FK references it)
```

This order is correct. Migration A (pos_import_profiles) must be dropped last because `invoices.source_profile_id` holds a FK to it. Dropping `invoices.source_profile_id` in the Migration B rollback step removes that FK before the table is dropped in the Migration A step.

## Data Loss Risk Assessment

| Risk | Severity | Conditions |
|------|----------|-----------|
| Loss of `voucher_classes` seed data | **None** | Can be regenerated by re-running migration 051 |
| Loss of `customer_masters` rows | **None** | Table is empty in Phase 1; no customer data was inserted |
| Loss of `pos_import_profiles` rows | **None** | Table is empty in Phase 1; no profiles were configured |
| Loss of `invoices` new columns | **None** | All values are uniform defaults or NULL; fully derivable |
| Loss of `vendor_ledger_preferences` new columns | **None** | All values are uniform defaults; fully derivable |
| Loss of purchase learning history | **None** | `vendor_key`, `ledger_type`, `ledger_name` are untouched |
| Loss of historical invoice data | **None** | Only new columns are removed; all original columns preserved |

**Conclusion**: The Phase 1 rollback has zero data loss risk under Phase 1 conditions (no customer learning written, no POS profiles created, no customer masters created).

**The one condition that would create data loss**: If `party_type = 'customer'` rows were inserted into `vendor_ledger_preferences` before rollback, those rows would lose the `party_type` distinction on rollback (the rows remain, but the column is dropped). Phase 1 explicitly prohibits this — validation check #17 in `phase1_validate.sql` enforces it.

## Rollback Order Validation

The dependency chain that governs rollback order:

```
invoices.source_profile_id  →  (FK)  →  pos_import_profiles.id
```

This means:
1. `invoices.source_profile_id` column must be dropped (Migration B rollback) **before** `pos_import_profiles` table is dropped (Migration A rollback).
2. The rollback script correctly does B before A.

All other rollback steps are independent of each other (columns on different tables, no cross-table FK dependencies introduced by Phase 1 other than the one above).

---

## Rollback Safety Properties

- **Transactional**: The entire rollback runs inside `BEGIN; ... COMMIT;`. If any statement fails, all statements are rolled back — no partial state.
- **Idempotent**: All statements use `DROP ... IF EXISTS` and `DROP COLUMN IF EXISTS`. Safe to run on a database where Phase 1 was only partially applied.
- **Non-destructive to existing data**: The rollback touches only Phase 1 additions. All original columns, tables, indexes, and data remain exactly as they were before Phase 1.
- **Does not touch RLS policies on existing tables**: Phase 1 only added RLS policies to new tables (`pos_import_profiles`, `customer_masters`). These are dropped with the tables.
